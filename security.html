On Security

The AI writes the same code for everyone. Understanding it is the rare part.

The real risk of building fast, with AI or without, is not that the app won't work. It's that it will work perfectly right up until the morning you find out it has been quietly readable, drainable, or bootable by someone who was never supposed to touch it. Generating that code is easy now. Knowing exactly what it does, and catching what it quietly got wrong, is the part that still takes real experience. That is the part I do. Here is a sample of what I close before I hand anything over.

The failure classes

Same seven mistakes, over and over.

None of these are exotic. They are the boring, common ways a fast-built app gets owned. Boring is exactly why they get skipped.

01

Secrets in the browser

The failure. The database or payment key ends up in the JavaScript bundle the browser downloads. Anyone can open dev tools and read it. This is how a vibe-coded app gets its database drained overnight.

How I close it. Secrets live server-side only, scoped to the least they need, and rotated. Nothing sensitive is ever shipped to the client. I check the built bundle, not just the source.

02

Authorization checked in the wrong place

The failure. The app hides the "delete" button for non-admins and calls it secure. The API still does the delete for anyone who asks. Every record is readable by every logged-in user.

How I close it. Access is enforced at the data layer, where a hand-crafted request can't route around it. Role checks plus per-record ownership, so a valid login still can't reach a record outside its scope.

03

Endpoints with no ceiling

The failure. No rate limit, no cost cap. One script hammering a usage-billed endpoint turns your monthly bill into rent, or takes the service down for everyone.

How I close it. Rate limiting, lockouts on repeated auth failures, and hard cost ceilings on anything that fans out to a paid API. The abuse case is handled before it's abused.

04

Queries built by gluing strings

The failure. User input concatenated straight into a database query. It's the 1998 vulnerability, and AI will generate it fresh in 2026 if nobody is watching.

How I close it. Parameterized queries throughout, input validated at the edge, uploads checked by their actual file signature rather than a trusted filename.

05

Auth that only looks like auth

The failure. Weak password hashing, no second factor, and sessions that never expire. One phished password owns the whole account forever.

How I close it. Modern password hashing, short-lived access tokens with rotating refresh and reuse detection, and real app-based two-factor. I built this for a live clinical platform, so it isn't theoretical.

06

PII leaking into logs

The failure. The quickest way to debug is to log the whole request. Now personal data is sitting in plain text in a log file and shipped to a third-party dashboard nobody audited.

How I close it. Logs run through a redaction allowlist, so sensitive fields never land in a log line. On regulated data, that's the difference between a bug and a breach notification.

07

A supply chain nobody watches

The failure. A few hundred dependencies pulled in and never looked at again. A known-vulnerable package sits there for a year because no one is checking.

How I close it. The build fails on any new high-severity advisory. On my clinical platform, every accepted exception is written down with why it's safe here and the exact condition that clears it. That discipline stops the breach nobody saw coming.

This is the public list. It's the common stuff, the things I'd expect any serious engineer to close. The longer list, the failure modes I've actually found in real code and the specific ways I close them, is the part you're hiring. Some of it stays in the workshop.
Why this matters more with AI, not less

The generation is the easy 80%. The review is the job.

Everyone can produce working code now. That's precisely why the value moved. When the first draft is free, the whole job is the judgment that comes after: knowing which of these seven the model just quietly introduced, and closing it before it ships. That is a skill the prompt doesn't have and most people skip.

So the honest pitch is this. Hiring someone who works with AI is not the risk. Hiring someone who works with AI and doesn't read the output is. I'm the first kind.
