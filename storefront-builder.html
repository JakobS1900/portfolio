Storefront Builder

Artists sell commissions from pages they host on Markdown paste sites. They do not know Markdown, so they pay someone who does. This turns that into a compiler problem: a block document in, host-correct Markdown out, with a warning for every compromise made on the way.

TypeScriptZero runtime deps Golden-file testsVitest axe-coreOffline PWA Capacitor / AndroidVerified on device
Use it here, and read the source at github.com/JakobS1900/markdown-storefront-builder. The engine is a few hundred lines of pure functions with no dependencies. Every architecture review and every bug it caught is committed alongside the code, including the ones that make me look slow.

The job

Go and look at how illustrators sell work. A large share of them run their commission page on rentry.co or something like it: a free Markdown paste site, no account, no platform cut. It is a genuinely good choice, and it has one problem. The page is written in Markdown.

So people who draw for a living end up learning table syntax, or paying someone forty dollars to lay out a price list. The gap is not talent or taste. It is a text format.

blocks -> document -> target capabilities -> markdown + diagnostics

The obvious build is a WYSIWYG editor that emits Markdown. That is the version I did not build, because it hides the actual difficulty. Every host renders a slightly different dialect, so the same page is correct on one and broken on another, and the artist finds out after they publish.

What shaped it

  • It is a compiler, not an editor. Blocks become a document, a per-host emitter turns that into Markdown, and a lint pass reports every compromise. That last part is the product: it is the thing an artist would otherwise pay a person to know.
  • Hosts are data, never code. A supported site is a record of capability values with a cited source for each one. No emitter branches on which host it is compiling for. A test proves it by inventing a host inside the test and compiling against it, which only works if the claim is true.
  • Nothing an artist types may become structure. Their text lands on a page hosted on someone else's domain, whose sanitizer I cannot inspect. So the escaper emits HTML entities rather than backslash escapes: the character is absent from the output entirely, and no renderer can build a tag out of what is not there.
  • Losing their page is the one unforgivable failure. The document format is versioned, a page from a future version is refused rather than guessed at, and a page that cannot be opened can still be downloaded exactly as it was saved.

The guards, and what they caught

I ran an architecture review before writing each feature and a holistic review across the whole diff after. Both are committed. Every one of the bugs below would have shipped, and not one of them was the kind a test I had already thought to write would catch. The later ones came from putting the app on a physical phone and then from someone else using it, both of which have their own sections further down, because holding the thing found what reading it did not.

Architecture review · feature 001

The writer could destroy a page on the way to disk

JSON.stringify turns NaN and Infinity into null, and null is never valid in this format. Neither can arrive by parsing, since neither is legal JSON, but both arrive easily from an editor field computed as parseInt(""). A page would have been written in a state that could not be read back: work destroyed by the save path itself. The writer now validates before it writes.

Holistic review · feature 001

Validation handed back the caller's own object

The editor validates a draft it is still holding, so the application's saved page and the page being typed into were one object. The saved copy changes underneath the app, silently, with no write and no event. Every function was individually correct, and no per-chunk test could see it, because within one chunk there was never a second holder of the object. It surfaces months later as a storage bug in a file nobody connects to this one.

Holistic review · feature 002

Two languages that disagree about what whitespace is

A newline inside a heading ends the heading and turns everything after it into body text, so the escaper collapsed whitespace with JavaScript's \s. That does not include U+0085. Python's splitlines does, and rentry is a Python service. A heading could pass our check and still be cut in half by the renderer. The escaper now collapses the union of both sets.

Pasting output into the real host

The line break the specification promised does not exist

Every capability value cited rentry's documentation, which is evidence and is not the same as having tried it. So I pasted the compiled output into their editor and read the preview. The hard line break, written as a trailing backslash because that is what CommonMark says, produced no break at all: rentry runs Python-Markdown, which does not implement it. Worse, the backslash was swallowed, so two sentences rendered as "each.Refunds". No test caught it, because every test asserted the backslash was emitted. The tests encoded the same assumption as the code. Only the renderer disagreed.

First run of the app

The first thing a new user does broke saving

Adding an "About you" section creates a profile with no name yet, and the schema marked that field non-empty, so the page became unsaveable before the artist typed anything. The fix was not placeholder text, which puts words in their mouth. The constraint was in the wrong place. An empty name is a valid document; it is a page that renders oddly, and this project's rule is that the compiler warns rather than the format refuses. Emptiness is a publishing concern, not a storage one.

Preparing the phone upload test · accessibility

The gate was passing on code it had never rendered

The image upload control is only built when an API key is present at build time, and the test run never set one. So the accessibility gate, the one thing standing between me and an unusable control, had been reporting green on a component it had never once put on the page. The moment a key existed it failed immediately: the file input had no accessible name, so a screen reader met an unlabelled second control for the same action. A gate that cannot fail is worse than no gate, because it is also collecting trust.

On a phone · checked against the live API

An error message that told the artist to wait forever

A refused upload showed "wait a few minutes", which is right for rate limiting. I checked what a bad key actually returns instead of assuming: Imgur answers POST /3/image with 429 Too Many Requests, byte for byte identical to a real limit, while /3/credits answers 403 "Invalid client_id". So a build with a dead key would have told every artist to be patient, on every upload, forever. The two cases cannot be told apart from inside the app, so the message now covers both rather than promising one.

On a phone · the Android build

The app served itself an older copy of itself

The offline service worker earns its place on the web. Inside the Android package every asset is already on local disk, so it cached nothing useful and instead shadowed the app's own files with the previous build. An install containing one bundle served the one before it, and the update only appeared on a second launch. Declining to register it would have fixed nothing for anyone who already had the app, since the registration and its cache survive an update, so the native build now tears both down. Verified by watching the handover across three launches on the device.

Reported by the owner, minutes into using it

Typing one character closed the keyboard

Type a letter into any field and the field went away. Type the next and it went away again, so the only way to enter a heading was one character at a time, reopening the field between each. Two faults compounding: the interface rebuilds its whole DOM on every state change, and a keystroke is a state change, so the element holding the caret was destroyed on every letter. Field ids came from a counter that only ever climbed, so nothing could find the field again afterwards. Fixing focus was not enough. One rebuild cost 37ms on that phone and every character caused two, because reporting "Saved" is also a state change, so roughly 75ms of blocked main thread per key. The WebView discarded anything typed at speed: AriDrawsCommissions arrived as Ari. Now 1.9ms, once.

Driving the app with real taps · Android

The keyboard took the screen away twice

Opening the keyboard collapsed the usable page from 672 to 114 CSS pixels: a sliver of the form, the tab bar jumping up beneath it, and a dead band the height of a second keyboard below that. Measuring the native view tree showed the window resize was correct and the WebView was not, by exactly the height of the keyboard:

parent FrameLayout [0,110][1080,1361] 1251px correct WebView [0,110][1080,452] 342px 909px short

Capacitor picks its inset strategy by reading the page's own viewport meta tag. Finding viewport-fit=cover on a recent WebView it takes a branch written for Android 15, where the window is edge to edge and is never resized, and pads the WebView's parent by the keyboard height. Unlike the branch directly below it, that one carries no OS version guard. On Android 10 the window had already shrunk, so the keyboard came off twice. Deleting one attribute routed it to the guarded branch and gave the screen back.

Driving the app with real taps

My own fix had missed the state he was actually in

I had already reworked the price list so a new section arrives with an empty item ready to type into, verified it on the device, and reported it done. His saved section held zero items, and a section with zero items rendered no fields at all: a button offering to add "another" item that did not exist, and a folded settings group. That is every section saved before the change, and every section whose last row is deleted. I had verified the fix against the state I created rather than the state he was in. An empty section now draws a placeholder row that joins the document the moment it is typed into, so "no items" stays a state the file can honestly hold.

Typing on the phone · caused by the fix above

The keyboard hands text to an element, and I kept replacing it

Typing "Full colour bust" into that new placeholder row produced "Ful colour bust". Three runs in eight lost a character, always the one straight after the first keystroke.

The app was not losing events. It applied every one it received: the number of beforeinput events always equalled the length of the value, so the character never reached the page at all. The convenient conclusion was that the test harness drops keys. A bare page with one input and no application code, driven by the same injection at the same speed, lost nothing in six runs, which took that excuse away and pointed back at me.

Android binds the keyboard to the focused editable through an InputConnection. A repaint rebuilds the DOM, so the focused input becomes a different element, the connection is torn down and rebuilt, and a character committed during the gap has nowhere to land. Tagging every element and recording which one each keystroke hit made it exact:

empty section, first key adds a row 2 nodes, 1 swap 3 of 8 dropped section that already has a row 1 node, 0 swaps 0 of 8 dropped

My own earlier fix caused it. When I made repaints wait for a pause in typing, I exempted changes to the shape of the page. Typing the first character into a placeholder row genuinely adds a row, which is a shape change, so it repainted at once, mid-word. Repaints now wait whenever a field has focus, whatever changed. Same experiment afterwards: zero drops in eight runs, and no element swapped mid-word in any of them.

On the phone · the button that lied

Both save buttons did nothing, and one said it had worked

A download attribute on an anchor is the whole story in a browser and does nothing at all inside a WebView, which ignores a blob: link unless the native side handles it. Nothing did. Pressing both export buttons produced no file in Downloads, none in shared storage, none in the app's own sandbox, and nothing in the system log. The app announced "Downloaded a backup" anyway.

That button exists to rescue someone's only copy of their page, so it was the worst thing on the page to be wrong about, and the same code backed the recovery button for a page that cannot be opened at all. Neither web escape hatch was available: navigator.share is absent in this WebView, and showSaveFilePicker exists but rejects instantly without showing anything, which is worse than being absent.

So the shell writes the file into its own directory, which needs no permission, and offers it through the file provider the manifest already declared. Android's share sheet decides where it goes, and no dependency was added. The page now reports what happened rather than assuming: a bridge that returns an error, or throws, counts as failure and says so.

Reviewing the code afterwards

The one file that could produce an executable address had no test

The preview renderer turns compiled Markdown into DOM. It is the only place in the application that builds an href or a src out of text, so it is the only place an artist's words could become something a browser acts on. It had no test at all: nothing anywhere imported it. Its own comment said "the XSS corpus test asserts exactly that". There was no such test.

The design did hold, for a reason worth stating. The link pattern needs ]( adjacent, and the escaper turns an artist's parentheses into escaped ones, so a refused link arrives as \[click\]\(javascript:... and the backslash between them stops the match. True, and load-bearing while living in a different module with nothing asserting it. Breaking that coupling on purpose produced seven live javascript: addresses.

The scheme is now checked where the value is used, as well as where it is produced. Breaking the coupling again now produces nothing, so the two defences are independent rather than one defence and one assumption.

Opening it on a desktop · caused by an earlier fix

Every form quietly undid the field before it

Type an item name, move to the price, and the name reverted. Typing the same two fields on the deployed app with different pauses between them puts the cause beyond argument:

pause 0ms -> {"name":"seed","price":"120"} the name was lost pause 120ms -> {"name":"seed","price":"120"} lost pause 250ms -> {"name":"Full colour bust","price":"120"} kept

The boundary is exactly the repaint delay, which is where it came from. Repaints wait for a pause in typing, so between keystrokes the controls on screen are older than the document. Every handler was built during the last render and closed over the section as it was then, so a second handler rebuilt the section from a stale copy and reinstated what the first had changed. It was not confined to prices: all five section kinds lost data the same way. Handlers now read the section as it is at the moment they run.

Silent data loss in every form in the application, caused by the fix for the typing bug two cards above, and found because I noticed a screenshot showing an empty field I had just typed into. No test caught it. There are five now.

Asked where the desktop version was

Nobody had ever opened it on a computer, including me

Every test I had run was at phone width or on the phone itself. Asked where the PC version was, I opened the URL that had been live for two weeks. The navigation bar was sitting in the middle of the page, below the editor: it is the last element in the document, which is right while it is pinned to the bottom of a phone and wrong the moment the wide-screen rule makes it static. Text fields ran 1088 pixels wide.

And the wide-screen rules in both the stylesheet and the shell were introduced as "Build beside Preview, since there is room to see both". There was no split view and there never had been. Two files had described an intention as though it shipped, which is exactly why nobody went looking for it, the same failure as the corpus test above. It exists now, and it is the one thing a desktop offers that a phone cannot: watching the page take shape without switching away from what you are typing.

Back on the phone · found in a fix I had called verified

My verification relaunched the app between every case

Back had been made to return to the previous screen instead of closing the app, and I had checked it: from Preview it went to Build, from Copy it went to Build, from Build it left. Every one of those was true. Walking the paths a person actually walks, without restarting in between, was not:

Build -> Preview -> Copy then back -> Preview Build -> Preview -> Copy -> Build -> Copy then back -> Preview

I had pushed a history entry for every move, which gives plain browser semantics: back retraces. That is right for pages and wrong for a tab bar whose first screen is Build, and the stack grew without limit, so toggling tabs ten times took ten presses to leave the app. At most one entry now exists beyond the first screen.

The interesting part is not the bug, it is that my check could not have caught it. Relaunching between cases reset the history every time, so the state the defect lives in was destroyed before each measurement. Each case passed honestly and the sequence was never tested. That is the same failure as a suite that sets a field's value in one assignment: not a wrong answer, a question that could only ever come back clean.

Pasted into the real host · the price bug

An artist writing "$45" published "\$45"

The escaper backslashes every character that could begin a Markdown construct. Its own comment justified the breadth: a wide list is safe, and the artist never reads the source. Both halves were wrong. The Copy screen shows them the source, it being the entire output of the tool. And rentry renders with Python-Markdown, whose escapable set is narrower than CommonMark's "all ASCII punctuation".

One paragraph per character, pasted into rentry's live preview:

honoured ` * _ { } [ ] ( ) # + - . ! | and a literal backslash visible ~ ^ $

So a price of $45, the likeliest input this application will ever receive, reached the artist's published page as \$45. The fix is the answer the same file already gives for <, & and >: a numeric character reference, which takes the character out of the source entirely so no renderer can build a construct from it, while every renderer displays it. Verified in the same session, including that &#126;&#126;text&#126;&#126; stays literal while a real ~~ is still struck through, so the protection survives.

The cause was a sentence, not a character. The capability record said escaping was standard, sourced as "documents no divergence from standard escaping", which is an absence of documentation written down as a presence of behaviour. The header of that very file forbids exactly that: a value may not be written from assumption, and an undocumented one is recorded as unknown. It is the second capability in that record written that way to turn out wrong. The first was the line break, four cards above.

Four hours later · caused by the card above

The fix broke the screen whose entire job is telling the truth

Moving three characters to numeric references stopped rentry publishing \$45 and started the preview showing the artist &#36;45. The preview renders the compiled output, so anything the compiler does for the host's benefit has to be undone there. It knew three named entities and nothing else.

The principle it broke is the one this project is built on. The preview exists to show what the host will actually produce, which is why it renders compiled output rather than an internal picture of the document. A preview showing plumbing is a preview lying, and it had been live for four hours.

Two things the fix had to get right, both now tested rather than asserted in a comment. Decoding a reference cannot produce markup: every result goes into a text node, so a decoded < is a less-than sign and never the start of a tag. And &amp; is decoded last, mirroring the escaper encoding it first, so an artist who literally types &#36; still sees &#36; rather than a dollar sign.

I found it before it reached the phone, by asking what the preview did with the new output instead of assuming a change to the escaper stayed in the escaper. That question is what a holistic review across the whole diff is for, and this change did not get one.

Exercising the warnings · the part that is the product

It told the artist to fill in a section they had just filled in

Pasting an unusable image address produced two notes about the same section. First "one of your images does not have an http address, so it has been left out", which is true and useful. Then "this section has nothing in it yet, fill it in and it will show up", which is false, contradicts the line above it, and sends someone looking for a second problem that does not exist. The preview then offered two ways back to that one section, with identical labels.

A section that produced nothing now says so only when nothing else has already explained why. Emptiness with a cause is reported as the cause.

This came from finally exercising the warnings rather than the editor. They are the product, in the sense that the compiler telling you what it compromised is the thing an artist would otherwise pay someone to know, and almost every check until then had been about typing, layout and storage. The same pass confirmed the two hosts really do diverge on the phone, rentry taking two trailing spaces where the portable baseline takes a backslash, and that a javascript: address reaches neither the preview nor the pasted output.

My first check of the fix said it had not worked. It had. A gallery left behind by the previous run meant I was counting notes across two sections and reading it as one section repeating itself. Restoring to a known document and counting by section rather than by the words on the button gave the real answer. Leftover state is its own way of asking a question that cannot come back right.

The unsaveable first run is the one I would want to be asked about. No test caught it, because every test I wrote encoded the same wrong assumption as the schema. It took opening the thing in a browser and clicking the first button.

The accessibility one is the sharpest, though, and it is the reason the three phone bugs are on this page at all. I had a green gate, a test count, and a habit of quoting both. None of that was worth anything for the control it never rendered.

Putting it on a real phone

The app is a Capacitor wrapper around the same code, because the web build was already offline and local, so there was nothing for a native layer to add except a launcher icon and a real file picker. Building an APK proves almost nothing, though, and I had written exactly that in the repository: it builds, nobody has ever tapped a button in it.

So I drove it on a Moto G7 over adb, evaluating against the WebView's own debugger, and checked the whole loop an artist performs: add a section, type a name, kill the app, relaunch it, and read the document back out of storage. Then compile, then copy, then paste it back to prove the text reached the system clipboard.

The first result was a false alarm, and the interesting part is how I knew. Nothing persisted, and the obvious reading was a broken storage layer on Android. Before touching the code I instrumented it: a 50ms timer never fired, while promises still resolved. That is not a storage bug, it is a stopped task queue. The screen had switched off, and Android freezes a hidden WebView, so indexedDB.open was sitting there returning no event at all: not success, not error, not blocked. One command to wake the screen and it opened first try. I had already reported it as a real defect, and had to go back and say so.

That is the honest shape of the work. Two of the three phone bugs above were found only because the first thing I found was not a bug, and I kept measuring instead of starting to fix.

Then the owner used it, and it was unusable

Everything above I found myself, on my own terms, with the app doing what I expected. Then Jakob opened the build on his own phone and typed a heading. One character, and the keyboard closed. His verdict was that it felt obviously machine-designed, overwhelming, clunky, and completely unusable. He was right on every count.

Five hundred and thirty tests were passing at the time. Not one of them could have found it, and that is the part worth explaining, because it was not bad luck. Every test I had written set a field's value in a single assignment and fired one event. A person does not do that. The defect lived entirely in the second keystroke, and my method was shaped so that a second keystroke never happened. The test count was not evidence of anything; it was a number I had grown used to quoting.

A green gate that cannot see the failure is the same problem twice. Earlier on this page, an accessibility gate reported green on a control it had never rendered. This is that shape again, in a different place: a suite that could not express the thing users do. Noticing the pattern the first time did not stop me shipping it the second.

So I stopped testing the app and started using it. I drove the real build on the Moto G7 with real Android input: taps sent through adb at computed screen coordinates, text through the actual keyboard, with the page recording every pointerdown so a tap that missed was reported as a broken harness rather than quietly accepted as a broken app. That found eight more defects in an afternoon, including two the fix above had left behind.

They were not exotic. Deleting a section was instant and irreversible from a control sitting between two harmless ones, 44 pixels apart, on a phone. An unfilled item pasted a row of empty cells into the artist's page. The row that opened a section read "Edit" whether it was open or shut, so the button offering to edit was the one that took the editor away. Empty sections vanished from the preview with no explanation, which reads as the tool losing them. Every one of those is obvious within a minute of using the app, and invisible for as long as you only run its tests.

Going back a second time found one more, and it was mine: the fix for the dead-end section had introduced a fresh way to drop a keystroke. That is the case for doing this repeatedly rather than once. A fix is a change, and a change is a thing that can be wrong.

The tests are still worth having, and there are more of them now, written to type character by character and to ask the document what is focused before each key rather than holding a reference. But I would not now describe a feature as done on the strength of a suite passing, and I would rather say that here than let a test count on this page imply otherwise.

The feature I removed on purpose

Image uploading worked. The picker opened, the file decoded, the request reached the host and came back. I took it out of the published build anyway, and I think that is the most senior decision on this page.

Uploading needs an API key, and a key shipped in a public bundle is shared by every artist who uses the site. It identifies the application rather than a person, so nobody's uploads land in my account, but the registration is mine and so is the responsibility: one artist posting something against the host's rules gets the whole application banned, and uploads then break for every user at once. The daily quota is shared the same way.

The tidy fix, asking each artist to register their own key, is worse than the problem it solves. Registering an API application is harder than learning the Markdown this entire project exists to remove. So the published build has no key, no upload button, and a field that tells an artist where to put an image and how to get its address back. That is what they already do today, and it costs nobody anything.

The upload path is still in the repository, still tested, and switched on by supplying a key in your own build. In the published bundle it is not hidden, it is absent: no endpoint, no key header, no image decoding, verified by fetching the deployed JavaScript and searching it rather than trusting the build log.

Three comments that stopped anyone looking

The same failure happened three times in this project, and it is the one I would most want to be asked about, because it is not a coding mistake. It is a documentation habit that disables the person who comes next.

  • "The XSS corpus test asserts exactly that." Written at the top of the only file that can turn text into a live address. There was no such test, and nothing anywhere imported the file.
  • "Build beside Preview, since there is room to see both." Introducing the wide-screen rules in two separate files. There was no split view in either of them.
  • "Read the current plan." The project's own instructions sent every new session to a plan finished a month and thirty five commits earlier, so each one began by reading a description of work already done.

None of these was a lie anyone told on purpose. Each was an intention written in the present tense and then left there. The cost is specific: a claim that sounds like a guarantee is a reason not to check, so the thing it describes goes unexamined for exactly as long as the comment survives. A missing comment leaves you curious. A confident wrong one leaves you satisfied.

All three are corrected, and the correction is not "delete the claim". Two of them are now true, because the test and the split view were built. The third names the gap it used to hide: the specification pipeline covers the first three features and stops, everything after that shipped without one, and the index says so on its front page rather than making a reader work it out from the file listing.

What is enforced, not merely intended

A project of this size accumulates good intentions. These are the ones wired to the build, so they fail rather than drift:

  • Engine purity is an ESLint rule. The engine cannot reference document, window, fetch, Date.now, or Math.random. I verified it fires rather than assuming it does.
  • Schema drift fails a parity test that snapshots every field name, type, and order. Changing the format is possible; changing it by accident is not.
  • Output correctness is byte-compared against checked-in Markdown files, kept readable so a human can judge a diff. The most valuable bug on this page was found by reading one of them, not by a test.
  • Accessibility runs axe-core over the rendered interface plus assertions a machine cannot make: that every control has a real name, that no placeholder stands in for a label, that the touch target minimum is actually in the stylesheet. Colour contrast is switched off with the reason stated, because the test environment lays nothing out and the number would be meaningless.
  • The gate now runs against the build that ships, not just the richer one. Which build gets tested used to depend on an environment file, so a contributor's machine and the CI checked different interfaces and neither said so. Tests that care about that difference now declare which build they are checking, and I confirmed the results are identical with the key present and absent.
  • The storage layer is tested against a real IndexedDB. It had no tests at all until the review that produced this section, despite being the module the project's own constitution guards most closely. Sixteen now, including the promise that a page this version cannot parse still comes back byte for byte. Confirmed they bite by storing the parsed object instead of the exact text, which is the shortcut that rule exists to forbid.
  • Typing is now tested by typing. The suite enters text one character at a time and asks the document what is focused before each key rather than holding a reference, because holding a reference is exactly the assumption that hid the worst bug on this page: the old node still accepts input, it is just no longer on the page.
  • Every gate on this list was checked by breaking it. Not by reading it and agreeing with it. I removed the label, removed the attribute, disabled the platform check, put the viewport attribute back, and watched each one go red before trusting it again. That habit is what turned the accessibility blind spot from a comforting green tick into a finding.

What I would tell you in an interview

For most of the build, the two shipped hosts produced identical output, and I wrote that down rather than manufacturing a difference to make the demo look better. The compatibility machinery was real and proved only by synthetic hosts in the tests.

That changed when I finally pasted real output into rentry, and it changed because the paste found a bug. They now differ on exactly one thing, the hard line break, and that difference exists because the renderer disagreed with the specification, not because it was designed in. Everything else in the current section types still renders the same on both.

What I would still tell you: one genuine divergence is a thin proof for an architecture this deliberate. The payoff arrives with a third host, or with a section type that uses rentry's own extensions. The machinery is right and it is not yet earning its keep, and I would rather say that than let a diagram imply otherwise.

Why this one is worth reading. Most portfolio pieces show a working thing. This one shows the working thing plus the reasoning that produced it, including the twenty seven times the reasoning was wrong, the time I called something a bug and it was not, the feature I deleted after building it, and the afternoon the owner told me the whole thing was unusable and it was. If you want to know how I would behave on your codebase, that is the part that generalises.
