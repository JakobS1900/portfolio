Storefront Builder

Artists sell commissions from pages they host on Markdown paste sites. They do not know Markdown, so they pay someone who does. This turns that into a compiler problem: a block document in, host-correct Markdown out, with a warning for every compromise made on the way.

The source is public and meant to be read: github.com/JakobS1900/markdown-storefront-builder. The engine is a few hundred lines of pure functions with no dependencies. Every architecture review and every bug it caught is committed alongside the code, including the ones that make me look slow.

The job

Go and look at how illustrators sell work. A large share of them run their commission page on rentry.co or something like it: a free Markdown paste site, no account, no platform cut. It is a genuinely good choice, and it has one problem. The page is written in Markdown.

So people who draw for a living end up learning table syntax, or paying someone forty dollars to lay out a price list. The gap is not talent or taste. It is a text format.

blocks -> document -> target capabilities -> markdown + diagnostics

The obvious build is a WYSIWYG editor that emits Markdown. That is the version I did not build, because it hides the actual difficulty. Every host renders a slightly different dialect, so the same page is correct on one and broken on another, and the artist finds out after they publish.

What shaped it

  • It is a compiler, not an editor. Blocks become a document, a per-host emitter turns that into Markdown, and a lint pass reports every compromise. That last part is the product: it is the thing an artist would otherwise pay a person to know.
  • Hosts are data, never code. A supported site is a record of capability values with a cited source for each one. No emitter branches on which host it is compiling for. A test proves it by inventing a host inside the test and compiling against it, which only works if the claim is true.
  • Nothing an artist types may become structure. Their text lands on a page hosted on someone else's domain, whose sanitizer I cannot inspect. So the escaper emits HTML entities rather than backslash escapes: the character is absent from the output entirely, and no renderer can build a tag out of what is not there.
  • Losing their page is the one unforgivable failure. The document format is versioned, a page from a future version is refused rather than guessed at, and a page that cannot be opened can still be downloaded exactly as it was saved.

The guards, and what they caught

I ran an architecture review before writing each feature and a holistic review across the whole diff after. Both are committed. Four of the bugs they found would have shipped, and none of them were the kind a test I had already thought to write would catch.

Architecture review · feature 001

The writer could destroy a page on the way to disk

JSON.stringify turns NaN and Infinity into null, and null is never valid in this format. Neither can arrive by parsing, since neither is legal JSON, but both arrive easily from an editor field computed as parseInt(""). A page would have been written in a state that could not be read back: work destroyed by the save path itself. The writer now validates before it writes.

Holistic review · feature 001

Validation handed back the caller's own object

The editor validates a draft it is still holding, so the application's saved page and the page being typed into were one object. The saved copy changes underneath the app, silently, with no write and no event. Every function was individually correct, and no per-chunk test could see it, because within one chunk there was never a second holder of the object. It surfaces months later as a storage bug in a file nobody connects to this one.

Holistic review · feature 002

Two languages that disagree about what whitespace is

A newline inside a heading ends the heading and turns everything after it into body text, so the escaper collapsed whitespace with JavaScript's \s. That does not include U+0085. Python's splitlines does, and rentry is a Python service. A heading could pass our check and still be cut in half by the renderer. The escaper now collapses the union of both sets.

First run of the app

The first thing a new user does broke saving

Adding an "About you" section creates a profile with no name yet, and the schema marked that field non-empty, so the page became unsaveable before the artist typed anything. The fix was not placeholder text, which puts words in their mouth. The constraint was in the wrong place. An empty name is a valid document; it is a page that renders oddly, and this project's rule is that the compiler warns rather than the format refuses. Emptiness is a publishing concern, not a storage one.

The last one is the one I would want to be asked about. No test caught it, because every test I wrote encoded the same wrong assumption as the schema. It took opening the thing in a browser and clicking the first button.

What is enforced, not merely intended

A project of this size accumulates good intentions. These are the ones wired to the build, so they fail rather than drift:

  • Engine purity is an ESLint rule. The engine cannot reference document, window, fetch, Date.now, or Math.random. I verified it fires rather than assuming it does.
  • Schema drift fails a parity test that snapshots every field name, type, and order. Changing the format is possible; changing it by accident is not.
  • Output correctness is byte-compared against checked-in Markdown files, kept readable so a human can judge a diff. The most valuable bug on this page was found by reading one of them, not by a test.
  • Accessibility runs axe-core over the rendered interface plus assertions a machine cannot make: that every control has a real name, that no placeholder stands in for a label, that the touch target minimum is actually in the stylesheet. Colour contrast is switched off with the reason stated, because the test environment lays nothing out and the number would be meaningless.

What I would tell you in an interview

Two hosts ship today, and they produce identical output for every current fixture. Both support six heading levels and both support tables, so nothing in the current section types distinguishes them. The compatibility machinery is proved by synthetic hosts in the tests rather than by a visible difference between the two real ones.

I could have manufactured a difference to make the demo look better. The honest position is that the architecture is right and its payoff is deferred until a third host or a section type that uses rentry's extensions. That trade is written into the review document, not discovered by whoever reads the code next.

The other thing I have not done: nobody has pasted the output into live rentry. Every capability value cites their published documentation, which is evidence, and it is not the same as having tried it. That gap is on the roadmap and labelled as the only claim in the project resting on trust.
